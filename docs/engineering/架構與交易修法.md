# 打卡系統：架構與交易修法規則

> 來源：2026-10-22 全系統寫入操作掃描與目標架構（摘錄，不含安全項）。給各修正工單共用。


整個後端只留一種寫法。掃描發現的問題（全專案 0 處交易、`storage.ts` 門面不接受交易、四份錯誤工具、員工端信任前端 ID）都從這裡收斂。

## 分層

| 層 | 位置 | 只做什麼 | 不准做什麼 |
| --- | --- | --- | --- |
| route | `server/modules/<m>/<m>.routes.ts` | 解析請求（zod）、取身分、呼叫一個 service 函式、回應 | import db、repository；寫業務判斷 |
| service | `server/modules/<m>/<m>.service.ts` | 一個業務操作＝一個函式；開交易、拿鎖、呼叫 core 判斷、呼叫 repository；交易提交後才呼叫 adapter | 直接寫 SQL；在交易裡呼叫外部系統 |
| repository | `server/modules/<m>/<m>.repository.ts` | 資料存取。每個方法最後一個參數是 `tx: Executor = db` | 業務判斷；呼叫其他模組 |
| core | `server/core/` | 純函式規則（勞基法、打卡判斷、時間、假日、燈號） | 碰資料庫、網路、框架 |
| adapter | `server/adapters/` | 外部系統（LINE、Ragic、Gmail、報名系統、試算表），逾時、重試、記錄成敗 | 碰資料庫（成敗紀錄除外，走 health） |
| infra | `server/infra/` | 連線、交易工具、鎖、session store、寄信傳輸 | 業務 |

`server/storage.ts` 刪除；呼叫端直接用該模組的 repository（跨模組讀資料時呼叫對方 service 的讀取函式，不直接用對方 repository）。以這條為準，總表 P9「模組間不得互相 import service」改讀為「不得 import 對方 repository」；service 之間的循環 import（例如 employee ↔ shift）在各批碰到時拆開，不新增。

## 交易與並行的固定作法（infra/db/tx.ts）

- `withTx(fn)`：`db.transaction(fn)` 的唯一入口；service 用它包住「一個業務操作的所有寫入」。
- `lockXact(tx, ns, key)`：`pg_advisory_xact_lock(ns, key)` 兩參數形式，`ns` 取自型別化的 `LOCK_NS`（101–113，見 `scan/總表.md` 第 6 節），字串鍵用 `hashtext`；只收交易物件，交易結束自動釋放。`withSessionLock(ns, key, fn)` 給要先抓外部資料的 Ragic 同步與排程。（10/22 U2 實作版，取代原本單一鍵寫法。）固定的鍵：
  - `clock:<員工>:<日期>`：打卡、補卡核准、打卡產生加班單。
  - `shift:<員工>:<日期>`：新增／修改／批次／匯入班表（勞基法檢查後寫入）。
  - `leave:<員工>:<年>`：請假申請、核准、駁回、取消（餘額）。
  - `summer:<週次>`：暑假發布、草稿儲存。
  - `sync:ragic-employees`：Ragic 全量同步（webhook、排程、手動共用）。
  - `job:<名稱>:<日期時段>`：排程每輪（多實例或重跑只會有一個真的做）。
- 狀態轉移一律「條件更新」：`UPDATE … SET status='approved' WHERE id=? AND status='pending' RETURNING *`，影響 0 列就回 409，不再先查再寫。
- 外部呼叫在交易外：先在交易內寫好業務資料（必要時寫一筆待送紀錄），提交後呼叫 adapter，再把成敗寫回。推播類用「先佔位、再推播、後記結果」。
- 冪等：webhook 事件、排程每輪、可重送的寫入請求都有冪等鍵；同鍵第二次直接回第一次的結果。

## 錯誤

- 只有 `server/shared/errors.ts` 一個型別：`httpError(status, message, extra?)`；刪掉四份 `err()`、`httpErr`、就地 `err.status =`。
- 一個全域錯誤中介層：帶 request ID 回應，伺服器錯誤寫入錯誤紀錄表（#5）。

## 啟動

- 不在執行期建表或改主檔：DDL 只透過 `shared/schema.ts`；`seed.ts` 只在空庫補初始資料，不覆寫既有場館半徑與座標；守則不在每次開機重建。
- 排程註冊集中一處，每輪拿 `job:` 鎖並記錄到健康狀態。

## 檢查（寫成測試，違反就紅）

- `layering.test.ts`：route 不 import db／repository；service 不 import 其他模組的 repository；沒有檔案 import `storage`。
- `purity.test.ts`：core 不碰 db／網路／框架（既有）。
- 新增 `no-raw-db.test.ts`：除 repository 與 infra 外，不准 import `db`。
- 每個標為「需交易／需鎖」的操作，補一條並行或中途失敗的整合測試（拋棄式 PG）。


## 6. 修法類型的通用作法

**A 交易。** 在 service 開 `withTx(async (tx) => …)`，把同一個 `tx` 傳給這個業務操作用到的每個 repository 方法。repository 方法簽名統一成 `(…args, tx = db)`，原生 SQL 也改成 `tx.execute(sql…)`，不再直接用全域 `pool`。稽核列、異動紀錄、計數更新跟主寫入在同一交易內，失敗就整筆回滾，不 catch 吞掉。補償寫入（先寫、失敗再改回去）一律刪除，交由回滾處理。批次操作先決定語意：全成全敗就一個交易；要逐筆成功就回傳逐筆結果，不能丟例外讓前端以為全失敗。

**B 條件更新。** 狀態轉移寫成一句 `UPDATE … SET status = $new, reviewed_by = … WHERE id = $id AND status = 'pending' RETURNING *`，回 0 列就回 409「已被處理」。不要先 SELECT 檢查狀態再 UPDATE。後續寫入（改打卡、改餘額）放在同一交易裡，只在拿到列時才做。同一個形式也用在樂觀鎖：`WHERE id = $id AND updated_at = $expected`，前端讀資料時拿 `updated_at`，送出時帶回來。還原、取消這類動作也加上前一狀態的條件（例如還原要 `status = 'cancelled'`）。

**C 互斥鎖。** 檢查後寫入（重複打卡、餘額夠不夠、勞基法、同日已填、空月）在交易開頭取 `pg_advisory_xact_lock(ns, key)`，交易內重讀資料再判斷再寫入，提交或回滾時自動釋放。一律用兩個參數的形式，第一個參數是命名空間，避免員工 42 和場館 42 搶到同一把鎖。第二個參數是整數 id；複合鍵用 `hashtext('venue:12:2026-07-01')`，碰撞只會多排隊，不會出錯。一個交易要拿多把同類鎖時依 id 遞增取，避免死鎖。

| ns | 名稱 | 第二鍵 | 用在 |
|---|---|---|---|
| 101 | 打卡 | employee_id | T01、T02、T05、T06、T10 |
| 102 | 假別餘額 | employee_id | T13 |
| 103 | 班表勞基法 | employee_id（多員工依 id 遞增） | T34、T35、T37、T40、T41、T42 |
| 104 | 班表區域月份 | `hashtext(region_id ‖ ':' ‖ 年月)` | T43 |
| 105 | 班格與模板 | venue_id | T44、T48、T50 |
| 106 | 暑假週次 | week_no | T65 |
| 107 | 補習班匯入 | 0 | T64 |
| 108 | 員工意願 | employee_id | T58 |
| 109 | 守則確認 | employee_id | T70、T88 |
| 110 | LINE 綁定 | `hashtext(line_id)` | T24 |
| 111 | Ragic 同步 | 0（session 層） | T73–T77 |
| 112 | 排程工作 | 工作編號（session 層） | B6 的每個工作 |
| 113 | 通知收件者 | `hashtext(lower(email))` | T30 |

打卡（101）與排班（103）分開，因為打卡不驗勞基法，共用會讓後台排班卡住員工打卡。

例外是 Ragic 同步與排程工作。它們要在「抓外部資料」之前就拿到鎖，否則擋不住舊快照覆蓋：A 先抓到舊資料，B 後抓到新資料，B 先寫完，A 才寫，結果新狀態被蓋回舊的。但依 F，交易裡不能等 Ragic。所以這兩類改用 session 層 `pg_try_advisory_lock(ns, key)`：從連線池借一條專用連線，拿到鎖後抓資料，再開短交易寫入，最後在 `finally` 用同一條連線 `pg_advisory_unlock` 並歸還連線。拿不到鎖就回 202 並記「待補跑」。不要把整個同步包進一個交易。

**D 唯一約束。** 只有在鎖擋不到所有寫入路徑、或既有資料已有重複時才用（目前只有 D1 必要）。流程固定：正式庫跑查重 SQL → 結果為 0（或使用者決定怎麼清）→ 索引寫進 `shared/schema.ts` → 推開發庫 → Publish 時看遷移提示。寫入端改成 `INSERT … ON CONFLICT DO NOTHING RETURNING`，或捕捉 23505 轉成 409。部分唯一索引的條件要跟查重 SQL 的 WHERE 完全一致。

**E 冪等鍵與事件表。** 一律新增表，不改既有表：
- `idempotency_keys (scope, key, result jsonb, created_at, PRIMARY KEY (scope, key))`：員工端與後台的「新增」類請求帶前端產生的 request id。在業務交易內先 `INSERT … ON CONFLICT DO NOTHING RETURNING`；拿到列才做業務寫入並把結果寫回；沒拿到就回傳已存的結果。和業務寫入同交易，業務失敗時鍵也一起回滾，可以安全重試。
- `line_webhook_events (event_id PRIMARY KEY, received_at, status, processed_at, error)`：驗簽後先寫入再回 200，衝突就略過；處理失敗留在表裡可重放。Ragic webhook（#2）用同一形式的另一張表。
- `push_dedup (scope, period, employee_id, ref_id, status, attempts, updated_at, PRIMARY KEY (scope, period, employee_id, ref_id))`：排程推播「先佔位、再推播、後記結果」。佔位成功才推；依 adapter 回傳把狀態標成 sent 或 failed；failed 下一輪可重試。推播後、記錄前當機留下的 pending，提醒類視為已送（最多一次），班表類可設定重推。
- 排程每輪：工作開頭取 C 的 session 鎖，同一工作同一時間只跑一個。

**F 外部呼叫移出交易。** 交易內只寫資料庫，提交後才呼叫 LINE、Ragic、Gmail、報名系統。呼叫結果要落地：推播寫進 `push_dedup` 的狀態，其他外部呼叫至少記到健康紀錄與錯誤表（#5、#7）。要在回應前送出的訊息（打卡回覆）放在提交之後、回應之前；可延後的放到回應後背景執行，但 autoscale 回應後不保證有 CPU，所以重要的要先落表、由排程補送。adapter 回傳改成 `{ ok: true } | { ok: false, reason }`，呼叫端必須處理失敗。讀外部資料（Ragic 抓取）放在交易開始之前。


**H 其他。**
- H1 單句 SQL：讀改寫或迴圈改成一句 `INSERT … ON CONFLICT DO UPDATE`（用既有唯一鍵）、`UPDATE … WHERE id = ANY($ids)`、`UPDATE … FROM`、multi-row insert；單句本身就是原子的。
- H2 業務規則修正：每項寫在該列備註，例如完整快照才停用、欄位所有權、diff 式發布、驗證順序、日期統一、負數不夾 0。規則本身移到 `server/core/`（U11）。
- H4 開機寫入改一次性 migration：seed 只補不存在的列、永不更新既有列；守則與管理員改成一次性資料 migration。
- H5 刪死碼或死分支。
