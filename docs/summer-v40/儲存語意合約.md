儲存佇列的資料形狀：

```ts
type DraftVersion = number & { readonly __brand: 'DraftVersion' };

interface LocalEdit { value: string; employees: EmployeeMeta[]; version: DraftVersion }

interface WeekDraft {
  weekNo: WeekNo;                                   // 送出時用它，不從畫面讀（劇本 4）
  base: { cells: Map<CellKey, string>; meta: Map<CellKey, EmployeeMeta[]>; serverUpdatedAt: string | null };
  local: Map<CellKey, LocalEdit>;                   // 尚未確認保存的修改
  headVersion: DraftVersion;                        // 每次修改 +1
  savedVersion: DraftVersion;                       // 伺服器已確認的最高版本
  inFlight: { version: DraftVersion; snapshot: { cells: Map<CellKey, string>; meta: Map<CellKey, EmployeeMeta[]> } } | null;
  phase: 'idle' | 'pending' | 'saving' | 'retrying' | 'blocked';   // blocked = 409 空白保護，不自動重試
  error: string | null;
}

// 不變式：hasUnsaved(d) === d.headVersion > d.savedVersion
```

流程：

1. **編輯**：`local.set(key, {value, employees, version: ++headVersion})`，排 900ms debounce。
2. **送出**：`inFlight` 有值就什麼都不做（回來後會自己再送）。否則 `snapshot = base ⊕ local`，payload 由 `payload.ts` 從 snapshot 純算，`weekNo` 取 `draft.weekNo`，記 `inFlight.version = headVersion`。
3. **成功**：`savedVersion = inFlight.version`；`base = inFlight.snapshot`、`serverUpdatedAt = 回應 updatedAt`；刪掉 `local` 中 `version <= savedVersion` 的項目；`inFlight = null`；若 `headVersion > savedVersion` 立刻再送。
4. **失敗**：`inFlight = null`，`local` 不動。409 進 `blocked` 並顯示訊息；其他錯誤 2s、4s、8s、10s 退避。
5. **輪詢**：GET 回來後，`local.size > 0`、`inFlight` 有值、週次不是目前週、或 `updatedAt` 不比 `base.serverUpdatedAt` 新，任一成立就丟棄回應；否則 `base = 遠端`。
6. **切週**：只切換顯示的 `WeekDraft`，舊週的佇列帶著自己的 `weekNo` 繼續送完。
7. **離開頁面**：任何一週 `hasUnsaved` 時掛 `beforeunload` 提示（v40 沒有，新增行為，S24）。
8. **發布**：等目前週 `hasUnsaved === false && inFlight === null` 才送 E11。

驗收測試：4.6 的四條劇本照抄成 `draft-store.test.ts`（vitest fake timers，fetch 用假伺服器給固定延遲），每條斷言「React 版驗收」那一句。

跨裝置的整週後寫者勝問題（G4 第 1 列）不在前端能完全解決。佇列已經把遠端變更合進 `base` 再送，但兩台同時存仍是整週覆寫。後端加 `expectedUpdatedAt` 樂觀鎖後，佇列在 409 衝突時要「拉遠端、把 `local` 疊上去、再送」，這一步保留介面，等後端改完再接。

### 4.6 Issue #9：三條劇本與實跑結果

**怎麼重現。** `tools/issue9_harness.js` 把 v40 的真實程式碼按行號抽出（`saveToServer`、`scheduleAutoSave`、`startSyncPolling`、`setCellValue`、空白保護），接上假伺服器與虛擬時鐘。以下三段是**模擬**，不是 v40 原碼：`collectSchedulePayload` 只組 rawEntries（照 L3895-3896）；`render()` 只記錄次數；`switchWeek` 照 L5719-5725 手寫。編輯走 `setCellValue + scheduleAutoSave`，等同員工彈窗與舞台排班的路徑（V024、V046）。這條路徑寫的是 duty 格或 meta，`saveToServer` 的 flush 救不回來；如果改成在可見的課程格直接打字，flush 能救回文字，但救不回 meta（R096）。

固定參數：初始伺服器第 1 週 `X=old`，本機已水合；GET 預設延遲 100ms。

harness 的限制：v40 的存檔 payload 有兩個來源，`rawEntries` 取自 state（L3895），`assignments` 與 `shifts` 取自 DOM（L3671-3716）。harness 只模擬前者，後兩者是空陣列。所以下面的「server」只代表草稿 `rawEntries`；發布用的 `shiftEntries` 會怎樣，各劇本另以「推論」說明。

#### 劇本 1：舊請求完成就清掉未存旗標，畫面顯示「已儲存」

步驟：
1. t=0 修改 Y=A（自動存檔排在 t=900）。
2. t=900 送出 POST#1，伺服器延遲 2000ms（t=2900 回來）。
3. t=1500 修改 Z=B（自動存檔排在 t=2400）。
4. t=2900 POST#1 回來。

v40 實跑結果（`node tools/issue9_harness.js` 的 S1）：
```
t=2400ms SNAPSHOT autosave timer for B fired while _isSaving: dirty=true status="待自動儲存" local={"X":"old","Y":"A","Z":"B"} server.w1=["X=old"]
t=2900ms SNAPSHOT POST#1 returned: dirty=false status="已儲存 09:00" local={"X":"old","Y":"A","Z":"B"} server.w1=["X=old","Y=A"]
```
錯誤：t=2400 的自動存檔遇到 `_isSaving` 直接 return（L3532），沒有重排。t=2900 POST#1 成功，把 `_dirty` 清成 false（L3563），狀態顯示「已儲存」，但 Z=B 根本沒送出。

React 版驗收：t=2900 時 `hasUnsaved` 必須仍是 true，狀態不得顯示「已儲存」。

#### 劇本 2：A 請求未完成時修改 B，之後必須再存 B，重整仍保留 B

步驟同劇本 1（S1 在 t=0 就啟動輪詢），再加：
5. 之後不再編輯，等到 t=20000。
6. 重新整理，也就是讀伺服器第 1 週。

v40 實跑結果（S1 後段）：
```
t=8000ms GET sent (returns at +100ms)
t=8100ms GET (sent t=8000ms) returned
t=16000ms GET sent (returns at +100ms)
t=16100ms GET (sent t=16000ms) returned
t=20000ms SNAPSHOT after 20s (no more edits): dirty=false status="已儲存 09:00" local={"X":"old","Y":"A","Z":"B"} server.w1=["X=old","Y=A"]
RELOAD would load server.w1 → Z present? false
```
錯誤：沒有任何機制再存 B。t=8000 與 t=16000 兩次輪詢都看到伺服器的 `updatedAt` 等於自己剛存的，所以不套用，畫面一直是 Z=B、伺服器一直沒有 Z。重整後 B 消失。

React 版驗收：POST#1 回來後立刻送 POST#2（含 Z=B），t≈4900 前伺服器有 Z；重整後 Z=B 仍在。

#### 劇本 3：背景同步不得覆蓋尚未保存的本地修改

步驟：
1. t=0 另一位管理員已存檔，伺服器第 1 週為 `X=other-device`，`updatedAt` 比本機新 60 秒。
2. t=8000 輪詢通過所有檢查（沒 dirty、5 秒內沒編輯、沒焦點），送出 GET，延遲 1000ms。
3. t=8500 修改 Z=C（自動存檔排在 t=9400）。
4. t=9000 GET 回來。
5. t=9400 自動存檔，POST 延遲 300ms。

v40 實跑結果（S3）：
```
t=9000ms SNAPSHOT poll GET returned and applied remote: dirty=false status="待自動儲存" local={"X":"other-device"} server.w1=["X=other-device"]
t=9400ms POST sent week=1 cells=["X=other-device"]
t=9800ms SNAPSHOT autosave for Z ran: dirty=false status="已儲存 09:00" local={"X":"other-device"} server.w1=["X=other-device"]
server has Z? false; renders after t=8000: 0
```
錯誤：輪詢只在**送出前**檢查 dirty（L3589），GET 回來後不再檢查就整批取代 state、清掉 dirty（L3612-3615）。Z=C 從 state 消失，900ms 後的自動存檔把「沒有 Z 的版本」存回伺服器，狀態顯示「已儲存」。因為剛編輯過不能重繪，畫面上的 DOM 還留著 Z，下一次 render 才消失。

實際後果比 harness 顯示的更糟（推論）：t=9400 那次 POST 的 `shifts` 是從還留著 Z 的 DOM 算出來的，`rawEntries` 卻是沒有 Z 的 state。結果是重新整理後草稿看不到 Z，但按「發布」時 Z 會被發到員工前台（發布讀 `shiftEntries`）。

React 版驗收：t=9000 時本機 Z=C 必須保留（遠端套用要嘛延後，要嘛只合併沒有本地未存版本的格）；t≈9700 伺服器要同時有 `X=other-device` 與 `Z=C`。

#### 劇本 4（衍生）：存檔剛回來、下一筆還沒送，此時切週

步驟：t=0 改 Y=A，t=900 POST#1（延遲 1500，t=2400 回來）；t=2000 改 Z=B（自動存檔排在 t=2900）；t=2500 切到第 2 週。

v40 實跑結果（S2）：
```
t=2400ms SNAPSHOT POST#1 returned, B not yet sent: dirty=false status="已儲存 09:00" local={"X":"old","Y":"A","Z":"B"} server.w1=["X=old","Y=A"]
t=2900ms POST sent week=2 cells=[]
week 1 on server has Z? false
```
錯誤：切週處理器看到 `hasUnsavedChanges()=false`，不 flush，直接 `resetScheduleState`，B 跟著消失。另一個時序（推論）：切週後真實的 `render()` 在 `loaded=false` 時用這台電腦 localStorage 裡的第 2 週舊值填格子；如果第 2 週的 GET 比 B 的 timer 晚回來，timer 觸發的存檔會把這些可見格 flush 進 state，等於把本機的第 2 週舊資料寫進 DB。原本給 B 的 timer 在 t=2900 照樣觸發，用第 2 週的週次送出一份空的 state。harness 沒有模擬真實 `render()` 對第 2 週發的 GET，所以「第 2 週被寫入空列」要看 GET 與 timer 誰先到；「B 遺失」不受時序影響，一定發生。另外 `saveToServer` 的週次從 `<select>` 讀（L3889），不是從待存資料本身讀，這是切週類錯誤的共同根因。

#### 由劇本推出的 React 版硬性需求

1. 每次修改都產生遞增版本號。請求回來時，只清除「送出當下版本以內」的未存標記；還有更新的版本就立刻再送一次（劇本 1、2）。
2. 存檔在途時的新修改，要排進佇列，不能被丟掉（劇本 1）。
3. 輪詢的 GET 回來**之後**要重新確認：沒有未存版本、沒有在途請求、回應的週次仍是目前週，才套用；否則丟棄這次回應（劇本 3）。
4. 每筆待存資料自帶 `weekNo`，送出時用它，不從畫面讀（劇本 4）。
5. 切週前要等佇列清空（或把舊週佇列帶著自己的 weekNo 繼續送完），不能看單一布林旗標（劇本 4）。
6. 409（後端空白保護）不可無限重試，要停下來並告訴使用者（E05）。
7. 存檔在途時按「發布」，要等佇列清空後再發布，不能誤報「儲存失敗」（R110）。
8. 同一次存檔的 `rawEntries`、`assignments`、`shifts` 必須從同一份 snapshot 純算，不可一部分讀 state、一部分讀畫面（劇本 3 的推論後果）。
